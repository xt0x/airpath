# Frontend Source Design

The frontend uses the Next.js `src/` directory convention for application route source.

- `src/app` owns App Router route segments, the root layout, and the small global stylesheet import for shared map/sidebar shell foundations.
- `src/components/app-sidebar.tsx` owns the documented application sidebar composition: static Airpath Ops identity, backend-aligned navigation groups, and rail.
- `src/components/ui` is reserved for shadcn CLI generated components. Airpath-specific behavior, labels, navigation content, and layout decisions must live in callers such as `src/components/app-sidebar.tsx`, feature components, or feature CSS. Do not add custom public APIs such as icon wrapper subcomponents to this directory unless the shadcn registry provides them.
- `src/components/ui/sidebar.tsx`, `sheet.tsx`, `button.tsx`, `alert.tsx`, `card.tsx`, `chart.tsx`, `command.tsx`, `popover.tsx`, `tooltip.tsx`, `calendar.tsx`, and the other UI files are generated from `components.json` using the `radix-nova` shadcn style. Callers use the generated public exports directly, including direct SVG children for button and alert icons, standard `Skeleton` instances for loading rows, and the standard `Progress` component for route and usage progress.
- `src/features/map-workspace` owns the Live Map application shell and Flight Search visibility state: airport-board discovery, secondary flight-number search, selected-flight summary, position facts, cache state, refresh controls, the horizontally centered and sidebar-top-aligned search layout, feature-local `map-workspace.module.css`, and composition of the sidebar with the fullscreen map.
- `src/features/map-workspace/lib/airport-board-controls.ts` owns airport selector options, airport label resolution, and local date-only parsing/formatting for the board controls.
- `src/features/map-workspace/lib/flight-search-selection.ts` owns the pure selection rule that turns a flight-number search response into the first flight ID to load on the map.
- `src/features/mapbox` owns the fullscreen Mapbox surface, native Mapbox route line and route endpoint label layers, current-aircraft marker rendering, and current-aircraft hover summaries.
- `src/features/mapbox/lib/aircraft-hover-card-formatters.ts` owns pure current-aircraft metric display formatting for hover cards.
- `src/features/mapbox/lib/geojson-coordinates.ts` owns reusable Mapbox-valid GeoJSON coordinate extraction used by route display and camera bounds logic.
- `src/features/mapbox/lib/map-layer-availability.ts` owns the shared availability policy that admits only displayable map-layer GeoJSON, including exact FlightAware planned routes and available actual/current layers.
- `src/features/mapbox/lib/map-camera.ts` owns route-aware Mapbox bounds calculation for aircraft and route focus requests.
- `src/features/mapbox/lib/map-route-layers.ts` owns native Mapbox route source and layer creation, deduplicated source data synchronization, and route paint repair after style redraws.
- `src/features/mapbox/lib/route-line-feature.ts` owns reusable finite-coordinate route line normalization, current-position coordinate appending, and geometry eligibility shared by Mapbox line sources and camera bounds.
- `src/features/mapbox/lib/route-layer-source-data.ts` owns the pure transformation from selected flight map data into the planned route, actual track, and endpoint FeatureCollections written to Mapbox sources.
- `src/features/mapbox/lib/map-theme.ts` owns reusable Mapbox paint theme tokens and builders for route lines and route endpoint labels.
- `src/features/flights/api` owns browser-facing adapters for the Airpath HTTP API, including airport-board, search, detail, map-data, position-history, refresh, and usage status requests.
- `src/features/flights/types` re-exports public flight API contracts from `@airpath/shared-types`, including map-rendering input shapes such as `FlightDetail` and the narrower `RefreshTaskType` contract used by browser-initiated refresh requests.
- `src/features/usage` owns the browser-rendered Usage & Limits workflow backed by `/v1/usage/status`, including feature-local `usage-workspace.module.css`.
- `src/hooks/use-mobile.ts` owns the shared 640px mobile breakpoint check used by the shadcn Sidebar. It exposes only the breakpoint constant, the pure width predicate, and the React hook while keeping browser media query snapshot/subscription details private.
- `src/lib/display-date-time.ts` owns human-facing UTC date-time formatting for backend ISO timestamps used by the Live Map search panel and map hover summaries.
- `src/features/flights/lib/public-flight-status.ts` owns frontend normalization for public English-only upstream flight statuses before search results, selected-flight summaries, or aircraft hover cards display them, including ASCII slash-separated status parts, ASCII space/tab edge cleanup, and an `Unknown` fallback for non-public or blank display text.
- Additional shared UI components and flight UI state hooks remain intentionally absent. Reintroduce them only with tests that describe the new visible behavior first.
- Test code belongs under `frontend/tests`, mirroring the source area it verifies. Production source directories under `src` must not contain `*.test.ts` or `*.test.tsx` files.
- Frontend source imports must use the `@` alias for any dependency that resolves under `frontend/src`. The alias is configured as `@/*` to `src/*` in TypeScript and Vitest, and `frontend/tests/architecture/import-alias-boundary.test.ts` guards that boundary. Relative imports remain acceptable only when they intentionally target files outside `src`, such as frontend root package metadata.

Keep Next.js configuration, package metadata, and environment examples at the `frontend/` root. Keep application route implementation inside `frontend/src/app`.

## Mapbox UI

`src/app/(app)/page.tsx` is a thin route entrypoint that renders the map workspace shell from `src/features/map-workspace/components/map-workspace.tsx`. The Flight Search experience is not a separate route; it is a state of the Live Map workspace opened by the sidebar action. App routes must not import flight feature UI, hooks, API clients, or fixtures directly.

The root layout owns metadata, the document shell, and the global CSS import needed by Mapbox GL and shared shell tokens. It applies the shadcn `dark` class to the document root and sets shadcn's default dark `--background` value, `oklch(0.145 0 0)`, inline on both `html` and `body`, so a reload cannot show the browser's default white background before CSS loads. The route loading state lives in `src/app/(app)/loading.tsx` and uses the shared shadcn Progress component with the documented `value` and `className` usage to show a compact map-reload progress indicator. The loading surface uses `--map-surface-background` and keeps only route-loading shell styling in global CSS. Live Map search-panel CSS lives in `src/features/map-workspace/components/map-workspace.module.css`, and Usage route CSS lives in `src/features/usage/components/usage-workspace.module.css`. The Mapbox component is a client component and dynamically imports `mapbox-gl` inside `useEffect` so server rendering and static builds do not touch browser-only Mapbox APIs. It delegates native route source and layer orchestration to `map-route-layers.ts`, pure route FeatureCollection selection to `route-layer-source-data.ts`, camera bounds calculation to `map-camera.ts`, map-layer availability policy to `map-layer-availability.ts`, finite-coordinate route line normalization and geometry eligibility to `route-line-feature.ts`, and reusable Mapbox-valid GeoJSON coordinate extraction to `geojson-coordinates.ts`. Planned route, actual track, and origin/destination endpoint GeoJSON attach directly to native Mapbox sources and layers so route geometry and airport-code labels are pinned to the same renderer as the base map during drag, zoom, pitch, and style redraws. Backend FlightAware planned route geometry is rendered as a dashed scheduled-route line, while actual track geometry remains solid; planned routes keep upstream fixes as anchors and may include backend great-circle display points for long-haul legs. Historical flights do not receive planned route GeoJSON, so inaccurate scheduled-route fixes cannot draw dashed geometry while final-track data is still loading. Both route lines use reusable `map-theme.ts` paint builders with the same `#facc15` yellow as the aircraft marker and `line-emissive-strength` so Mapbox Standard lighting cannot dim them in dark presets. Origin and destination endpoint annotations use only native Mapbox symbol labels derived from planned route geometry and selected flight detail; no start/end endpoint circle layer is rendered. The actual track display discards non-finite or out-of-range track coordinates before appending the available current aircraft position as the final coordinate, so the rendered track endpoint and route-focus bounds align with the aircraft marker without mutating cached backend data. Airport-to-airport fallback geometry, unavailable layer GeoJSON, and non-line route features are not rendered in Mapbox line sources and are not used for route-focus camera bounds. Route line source data is normalized to finite longitude/latitude pairs within Mapbox's accepted ranges before it reaches Mapbox. Endpoint labels require a drawable planned route line or segment with at least two valid coordinates, so degenerate planned-route features cannot create labels without route geometry. The current aircraft marker is a Mapbox DOM marker with a small React root mounted into the marker element so the same shadcn `HoverCard` summary can be used on the map marker. Marker DOM removal is immediate, while React root unmount is deferred to the next macrotask so Mapbox cleanup cannot synchronously unmount a nested root during React rendering. It uses the same lucide `Plane` icon as the Tracked Flights sidebar action, rendered as a filled `--airpath-map-aircraft-marker` CSS-token plane without a circular marker background. The marker is only rendered when current position data exists, and new marker instances receive their longitude/latitude before being added to Mapbox so route-only flights do not trigger Mapbox `LngLatLike` runtime errors. No duplicate fixed aircraft heading indicator is rendered in a viewport corner. The hover summary shows selected flight identity, route, status, aircraft type, registration, altitude, speed, and last update timestamp while keeping internal data source, heading, and map-layer diagnostics out of transient marker UI. `FullscreenMap` accepts an `aircraftFocusRequest` counter from the workspace; each new request flies the Mapbox camera to the current aircraft coordinates with a readable tracking zoom when a current position is available, or fits the map to the selected exact planned route, available actual track, and available current-position GeoJSON bounds when no current aircraft position is available. It observes the map canvas container with `ResizeObserver` for real viewport changes, but sidebar open and close do not resize the map container because the desktop sidebar overlays the map. The html element, body, Tailwind base body rule, sidebar wrapper, map inset, Mapbox screen, Mapbox-generated `.mapboxgl-map` container, Mapbox canvas container, and canvas all use `--map-surface-background`, which resolves to `var(--background)`, as their dark backing color. The base body rule must not reapply `bg-background`, because the root dark class already controls the shadcn background token and a mismatched body utility can flash during page reload before Mapbox has redrawn.

The map reads `NEXT_PUBLIC_MAPBOX_ACCESS_TOKEN` from the environment. The token must be a publishable browser token; API keys and secret Mapbox tokens must not be hardcoded or placed in browser-visible variables.

The map style reads `NEXT_PUBLIC_MAPBOX_STYLE_URL` from the environment. Empty or whitespace-only values fall back to `mapbox://styles/mapbox/streets-v12`.

## Live Map Workflow

The Live Map is centered on one selected flight, but the primary discovery path is now an airport board. `MapWorkspace` uses shadcn `Command` and `Popover` for the airport selector, shadcn `Calendar` and `Popover` for the board date picker, shadcn `Button` for board direction and Load/Search/Refresh actions, shadcn `Input` for the flight-number fallback, shadcn `Badge` for compact flight-data status labels, and shadcn `Spinner` for pending `Show on map` feedback. It then loads `/v1/airports/{airportCode}/departures` or `/v1/airports/{airportCode}/arrivals`. `airport-board-controls.ts` keeps the selectable airport list, ICAO/IATA lookup, display labels, and date-only parsing/formatting outside the React component so those transformations stay unit-tested. The selected airport is stored as the ICAO code expected by the API while the visible control shows the airport name plus IATA/ICAO codes. Metropolitan area codes such as `TYO` are not treated as airport selections. Changing the airport, board date, or departure/arrival direction clears the previous board response and selected-flight details so a stale flight route cannot appear under a new board criterion. Loading a board result list does not auto-select the first candidate, and each board result exposes an explicit `Show on map` action. Flight-number search remains as a secondary fallback for users who already know an ident; the input shows non-ANA/JAL examples using FlightAware-style ICAO airline prefixes, and when search returns results, the API order is `scheduledOut` ascending, the first result is selected automatically, and the same refresh/detail/map-data loading path is used so its route can appear without requiring a second click. The pure first-result selection rule lives in `flight-search-selection.ts`. Explicit `Show on map` activation records the pending map reveal flight ID, increments a flight-data request counter so retries for the same flight ID still run, requests position, route, and final-track refresh work, shows the spinner on the pending candidate while candidate buttons are disabled, reloads `/v1/flights/{flightId}` and `/v1/flights/{flightId}/map-data`, briefly retries those reads when a track task was accepted but actual track GeoJSON is not available yet, closes the search panel after those selected-flight payloads are ready, and increments the map focus request so Mapbox focuses the selected aircraft or route bounds. Automatic flight-number loading performs the same refresh/detail/map-data requests while keeping the search panel open. The optional `/v1/flights/{flightId}/positions` client method exists for position-history features, but the initial map does not render every history point by default. The root Live Map route starts with the search panel hidden. Pressing the sidebar `Flight Search` action inside `MapWorkspace` toggles the panel through `openSearchPanel` and `closeSearchPanel`, marks the sidebar action active with `activePath="flight-search"` while the panel is visible, and applies `live-map-panel--centered` so search is horizontally centered over the map. Closing uses the `closing` state and keeps the panel mounted for the 420ms `live-map-panel-exit` animation before returning to `hidden`; opening uses the matching 420ms `live-map-panel-enter` animation. The panel is positioned from `--live-map-search-sidebar-offset`, `--live-map-search-center-offset`, and `--live-map-search-top-offset`; those variables are driven by the sibling shadcn sidebar `data-state`, so the panel centers inside the visible map area while its top edge aligns with the Live Map menu hover row. The top offset is `6.5rem` while the sidebar is expanded and `4.5rem` while the sidebar is collapsed, matching the generated sidebar header, group label, and icon-collapsed label behavior. While visible, `MapWorkspace` listens for document-level `pointerdown` events and returns to the closing state when the pointer starts outside the search panel. Radix `PopoverContent` and the sidebar Flight Search trigger are treated as part of the search interaction surface so airport/calendar menu clicks and sidebar toggle clicks do not race the outside-click handler. Only the centered state applies `map-workspace__inset--search-focus`, which blurs and slightly scales `.mapbox-screen`; during `closing`, that class is removed while the panel is still mounted, allowing the map's 420ms filter/transform transition to release the background blur in parallel with the panel exit. The sidebar, sidebar trigger, and search panel remain outside the blur rule. The Load and flight-number Search actions share one fixed action-column width through `--live-map-panel-action-width`, so the flight-number input expands or contracts while both submit buttons stay aligned. All search surface corner treatments are normalized to 4px: the panel box, shadcn-backed buttons, input, airport/date popover layers, results, alerts, and compact status labels must not reintroduce 6px or 8px radii.

The visible panel shows flight ident/IATA, route, aircraft, registration, status, progress, current latitude/longitude, altitude, speed, heading, altitude-change, update type, source, and human-readable timestamps. It does not render map-layer diagnostics inside the search panel; planned, actual, and current map-data availability remains an internal Mapbox rendering concern unless a dedicated layer/debug view is introduced.

Manual refresh requests enqueue `position`, `route`, and `final_track` tasks for the selected flight and use the same short actual-track hydration retry as `Show on map`. The refresh button is disabled while loading, while refreshing, when no flight is selected, or when usage status reports fetching disabled, a budget stop, or an active rate limit. Cache metadata from the freshest available flight/map/search response is reduced to user-facing data status copy: fresh data renders as `Flight data` with an `Updated` badge and timestamp, while stale data renders as `Flight data may be outdated` with an `Outdated` badge. Internal cache source, checked time, stale time, and expiry time stay out of the general search panel.

## Sidebar UI

The sidebar uses the shadcn Radix Sidebar component generated by `shadcn add sidebar`. `SidebarProvider` wraps `AppSidebar` from `src/components/app-sidebar.tsx` and `SidebarInset`, matching the documented composition in `docs/slidebar.md`. `AppSidebar` keeps `collapsible="icon"`, renders `SidebarHeader`, `SidebarContent`, grouped direct menu buttons, and `SidebarRail`; it intentionally does not render a Teams switcher, Teams hover card, footer user, or operator account menu. Navigation is grouped around backend-supported workflows: `Workspace` contains `Live Map`, `Flight Search`, and `Tracked Flights`; `Data` contains `Usage & Limits`; `System` contains `Settings`. Fetch pipeline availability is surfaced through `Usage & Limits`, so the sidebar does not expose a separate `Fetch Status` entry. Map layer availability remains part of the map rendering workflow rather than a separate sidebar entry. When `AppSidebar` receives `onFlightSearchSelect`, `Flight Search` renders as a button action instead of a `/flight-search` link; outside the Live Map shell it links to `/?flightSearch=1`, and `MapWorkspace` opens the centered search panel from that query after the home route mounts. When `AppSidebar` receives `onTrackedFlightsSelect`, `Tracked Flights` renders as a button action instead of a placeholder link; outside the Live Map shell it links to `/?trackedFlights=1`, and `MapWorkspace` focuses the Mapbox camera on the current tracked aircraft from that query after the home route mounts. Route shells pass `activePath` when a menu item or action should render active. These entries remain direct top-level menu buttons so each keeps a visible collapsed rail icon. `AppSidebar` owns the application-specific collapsed icon classes: action buttons use explicit text sizing, labels hide in the icon rail, and the Airpath Ops identity keeps a 2rem `bg-sidebar-primary` square with a 4px radius without relying on global `data-slot` overrides. The trigger uses a lucide icon button and toggles the sidebar with click or `cmd+b` / `ctrl+b`.

`SidebarInset` owns the main map workspace. The Mapbox surface is absolutely positioned inside the inset so the map fills the full viewport. The desktop sidebar keeps shadcn's generated fixed sidebar container. The Live Map route adds `map-sidebar-layout` to `SidebarProvider` and scopes the generated sidebar gap to zero in global CSS, so the sidebar overlays the map without adding a custom `layout` prop to the shadcn Sidebar primitive. Layout-participating routes such as Usage omit that provider class and keep the generated reserved gap.

Global CSS owns only shared shell sizing, the trigger header, trigger icon color, trigger hover background, the `map-sidebar-layout` overlay gap rule, map canvas positioning, map-surface fallback backgrounds, sidebar-state sibling positioning for the map workspace, and the `md` breakpoint value that keeps Tailwind's sidebar display breakpoint aligned with the app's mobile breakpoint. It must not contain `live-map-panel` or `usage-*` selectors, hide `SidebarRail`, or add a non-hover background to the collapsed trigger. The collapsed rail remains visible with 2rem icon buttons and hidden labels from `AppSidebar` classes. The trigger toolbar has `pointer-events: none` so its transparent area cannot block collapsed sidebar icon clicks; the trigger button itself restores `pointer-events: auto`. The trigger normal and focus states stay visually transparent, while its icon uses `var(--foreground)` and its hover background uses shadcn's `var(--accent)` token. The trigger button radius is forced to 4px so the hover background box matches the Mapbox control corner radius instead of shadcn's default icon-button radius. The trigger transform is composed from separate `--map-sidebar-trigger-x` and `--map-sidebar-trigger-y` variables and transitions the single composed transform, so open/close animation does not temporarily drop either axis. When the sidebar is collapsed, the trigger x variable uses the icon rail width and the y variable uses `--map-sidebar-collapsed-trigger-y`, derived from the collapsed Airpath Ops identity icon center and toolbar center. This keeps the trigger vertically centered with the identity icon while placing it outside the icon box instead of overlapping it. When the sidebar is expanded, the map trigger x variable uses the full sidebar width so it remains reachable outside the overlaid menu. Layout-participating screens such as Usage keep their toolbar and trigger overrides in `usage-workspace.module.css`; Usage uses the same collapsed x origin as the map trigger and moves the toolbar to the full sidebar width only while expanded. The mobile sidebar uses the generated Sheet through the generated Sidebar primitive without Airpath-specific code in `src/components/ui`.

The mobile breakpoint hook exposes `MOBILE_BREAKPOINT`, `isMobileViewport`, and `useIsMobile`. `isMobileViewport` has direct unit coverage for the 640px boundary. `useIsMobile` returns `false` during server rendering and delegates browser updates to `useSyncExternalStore`. Its media query snapshot/subscription adapter is private implementation detail, and the architecture test keeps Tailwind's `md` breakpoint aligned with the exported hook breakpoint. `SidebarProvider` clears the transient mobile Sheet open state when the viewport returns to desktop so a previously opened mobile menu does not reappear after resizing back to mobile.

The sidebar menu background token resolves to shadcn's default dark `var(--background)` through `--sidebar-menu-background`. `--sidebar` references that token, while `--sidebar-border` references shadcn's `var(--border)` so the menu panel and its vertical border line follow the same default dark palette. Desktop sidebar side borders must use `border-sidebar-border` instead of hardcoded colors, otherwise the generated `border-r` / `border-l` utilities can render a mismatched vertical line while the menu opens. The menu background token is also exposed to Tailwind as `--color-sidebar-menu-background`.

## Usage Visualization Primitives

The shared UI primitives are limited to reusable shadcn building blocks generated under `src/components/ui`. `Command`, `Popover`, `HoverCard`, `Tooltip`, and `Calendar` support the Live Map airport-board search controls, Sidebar collapsed labels, and current-aircraft hover summaries without local custom combobox/date-picker code. `Button`, `Input`, and `Badge` cover airport-board direction actions, Load/Search/Refresh actions, the flight-number fallback, and compact cache/status labels. Button and alert icons are direct SVG children because the generated components style direct SVG descendants. `Skeleton` is used directly for placeholders, and callers choose sizing through class names. `Progress` is used by route loading and the Usage API cost card through the generated single `Progress` export. `Card`, `Alert`, and `Chart` provide the Usage & Limits information hierarchy using the generated shadcn public slots. Airpath-specific layout rules around these primitives belong in feature components and feature CSS, not in `src/components/ui`.

## Usage & Limits Workflow

`src/app/(app)/usage/page.tsx` renders the shared sidebar shell with the Usage &
Limits screen instead of the fullscreen map. The screen still fetches
`/v1/usage/status` through `AirpathApiClient` on the client. The presentational
surface is limited to operator decisions: month-to-date cost against the soft
stop threshold, active stop reasons, rate-limit reset time when applicable, last
checked time in the shared UTC timestamp format, and monthly API usage cost. The
view composes shadcn Card, Badge, Progress, Alert, and Chart primitives so each
section has a consistent header/content rhythm. The active usage month's
estimated cost is rendered as a chart because it is available directly from
`estimatedMonthToDateCost`; the last checked timestamp is shown under that chart
with the shared UTC display formatter, and the chart header shows only the usage
month. Cost versus soft stop is shown as numeric values and a progress indicator
in the API cost card. Loading and error details, fetch availability, cache
freshness, cache source, projections, and backend diagnostics are not rendered on
this screen.
`usage-status-summary.ts` owns the pure formatting and summary transformations
behind the component. `usage-workspace.module.css` owns the Usage page spacing,
scroll container, toolbar, and sidebar-state overrides so Usage selectors do not
live in `globals.css`. The Usage page content starts below the fixed sidebar
trigger toolbar with deliberate page spacing, while the inset remains the
scroll container because the root body is fixed for the map surface. The Usage
shell preserves `SidebarProvider` as the flex layout wrapper so the reserved
desktop sidebar gap can move the content when the menu opens instead of letting
the fixed sidebar cover the `Usage & Limits` heading.

## Flight API Boundary

The frontend still keeps the typed FlightAware API client because it is a non-UI adapter boundary. The API client builds all `/v1` endpoint paths through shared route builders from `@airpath/shared-types` after stripping trailing slashes from `NEXT_PUBLIC_API_BASE_URL`, which is treated only as an optional origin/base URL so frontend environment configuration cannot duplicate the API prefix. Local browser development uses the Go local API server at `http://localhost:8080`; deployed environments can use an API Gateway or custom API origin. Successful JSON responses are validated at the client boundary for airport-board, search, detail, map-data, position-history, refresh, and usage status by delegating to the shared `validateApiSchema` helper, so response shape, enum, nullable, and numeric-range rules stay aligned with the OpenAPI schema source instead of being redefined in the frontend. Legacy usage-status payloads that omit `budget.dailyUsage` are adapted to an empty chart series before schema validation and returned as normalized responses. Frontend source that needs flight API shapes imports them through `src/features/flights/types`; only this facade and the API route-builder adapter touch `@airpath/shared-types` directly. Manual refresh inputs use the shared `RefreshTaskType` subset instead of the wider fetch queue task type and are checked at runtime before POST, including non-empty task lists, unique task types, and the non-summary refresh enum, so browser code cannot request internal `summary` fetch work even if a caller bypasses TypeScript. Malformed upstream payloads, invalid refresh input, non-JSON HTML responses, and network-level fetch failures become typed retryable API errors instead of unchecked TypeScript casts, raw JSON parse exceptions, or generic browser `fetch failed` messages.

Workspace package imports resolve through package `exports` and built `dist` artifacts during frontend builds. The frontend `build:deps` script builds `@airpath/shared-types` before typecheck or production build, so clean CI workers have the declarations that package exports reference. The frontend `tsconfig` must not alias workspace packages directly to package `src` files because those sources use NodeNext `.js` import specifiers that Turbopack does not resolve as TypeScript source paths.
